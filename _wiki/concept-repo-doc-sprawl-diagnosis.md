## Summary
markdown 위주 리포의 문서가 불어났을 때, 군살은 "글이 많아서"가 아니라 **외부 상태를 리포 안으로 복사한 백업 디렉터리**에 몰려 있는 경우가 많다. 실제 진단에서 추적 문서의 18%가 백업이었고 그중 절반이 **백업의 구버전 스냅샷**, 즉 백업의 백업이었다. 지우기 전에 확인할 것은 딱 하나 — **생성 스크립트가 그 폴더를 다시 만드는가.**

## Key Facts
- 디스크 파일 수와 관리 대상 수는 다르다. `find` 는 `.venv`·`node_modules` 안의 서드파티 문서를 세고, 크기순 정렬에서는 라이브러리 CHANGELOG 하나가 1위를 먹는다 — **진단은 `git ls-files` 로 시작한다**
- 외부 상태(설정·메모리 등)를 리포로 복사하는 백업은 정상 설계지만, 사고 복구 때 만든 임시 사본이 눌러앉아 **같은 내용의 구버전 폴더가 영구화**되기 쉽다
- 백업 폴더 삭제 판단의 유일한 기준은 **생성기의 화이트리스트** — 스크립트가 만들지 않는 폴더만 안전하게 지울 수 있다
- 같은 파일이 두 곳에 있을 때 SSOT는 **참조 수로 정한다**. 17개 보유·10곳 참조 vs 5개 보유·1곳 참조면 답이 나온다
- 버전 체인(`-v2`, `-v3`…)은 삭제가 아니라 `archive/` 이동. 단 **이동과 참조 갱신은 한 쌍**이다
- 진단 범위와 실행 범위는 다르다. 소유권이 없는 영역(납품 폴더 등)은 세어만 보고 손대지 않는다

## Details

### 왜 백업이 최대 중복원이 되는가

원본이 git repo 밖에 있으면 리포만 백업해선 통째로 날아간다. 그래서 화이트리스트로
복사해 커밋 대상에 넣는 설계가 나온다 — 여기까진 옳다.

문제는 **그 백업이 한 번 사고를 겪은 뒤**다. 전형적 경로는 이렇다.

1. 백업 스크립트가 원본 경로를 하드코딩한다
2. 경로가 바뀐다 (사용자명·폴더 이동·툴이 만드는 slug 변경)
3. 스크립트가 "원본 집합이 비었다"고 판단하고, 정리 루프가 **백업을 전부 지운다**
4. 사람이 복구하면서 임시 사본을 옆에 만든다
5. 스크립트는 고쳤지만 **임시 사본은 아무도 안 지운다**

이 5번이 몇 달 지나면 "백업의 백업"이 된다. 원본과 diff 해 보면 차이가 몇 개 안 되고,
그 몇 개조차 이미 폐기된 항목이다. **git 히스토리가 모든 과거 버전을 갖고 있으므로
스냅샷 폴더가 따로 존재할 이유가 없다.**

### 삭제해도 되는지 판정하는 순서

```
1. diff -rq <원본> <리포안백업>     → 완전 동일한가 (정상 백업 확인)
2. 생성 스크립트의 화이트리스트 읽기 → 그 폴더를 만드는가
3. git grep "<경로>"                → 참조하는 문서가 있는가
```

2번을 건너뛰면 다음 실행에서 그대로 돌아온다. 3번을 건너뛰면 링크가 깨진다.

### 중복 두 벌 중 어느 쪽이 원본인가

파일 날짜나 폴더 이름의 "느낌"으로 정하지 않는다. **참조 수**가 답이다.

| 판단 근거 | 신뢰도 |
|---|---|
| 다른 문서가 그 경로를 링크하는 수 | 높음 — 실제 의존이다 |
| 보유 파일 수 (더 완전한 집합) | 높음 |
| 수정 날짜 | 낮음 — 복사만 해도 갱신된다 |
| 폴더 이름이 더 "정식"으로 보임 | 없음 |

SSOT를 정했으면 **인덱스의 링크와 "새 자료 추가 절차" 문구까지 같이 옮긴다.**
절차 문서가 옛 경로를 가리키고 있으면 다음 사람이 중복을 다시 만든다.

### 삭제 vs archive 이동

| 성격 | 처리 |
|---|---|
| 완전 중복 · 스테일 미러 | **삭제** (git 히스토리에 남음) |
| 미기입 스캐폴드 · 일회성 로그 | **삭제** |
| 대체된 버전 체인 (v1~v5) | **`archive/` 이동** — 판단 이력이라 본문 가치가 있다 |
| 소유권 없는 영역 | **손대지 않음** |

버전 체인을 옮기면 그걸 참조하던 문서들이 조용히 깨진다. 이동 직후
`git grep` 으로 잔여 참조 0건을 확인하는 것까지가 한 작업이다.
